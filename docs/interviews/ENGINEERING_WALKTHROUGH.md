# Engineering walkthrough

Lead with the implemented workflow: sign in through Keycloak, choose an authorized organization, register a synthetic device, create a policy, submit a simulator report, and inspect the persisted evaluation and audit event. Explain that FleetOps simulates inventory/compliance; it does not implement Apple MDM. Show the actual validation record and distinguish it from pending cloud/Docker checks.

1. **Why build FleetOps?** To practice an enterprise Java/Angular stack with meaningful security and data consistency requirements. Device compliance gives concrete domain rules beyond CRUD, without claiming access to real enterprise devices.
2. **Why Spring Boot rather than Node?** The project specifically develops Java and Spring Security experience. Constructor-injected services and a pure rules engine provide testable seams; this is a fit to learning goals, not a claim that Node is inferior.
3. **Why Angular?** Standalone components, reactive forms, HttpClient and Material provide a consistent enterprise client. Signals hold local request/UI state, and lazy routes separate inventory, policies, detail, audit and overview.
4. **Why a modular monolith?** One deployment avoids distributed operational complexity for a solo developer. Functional packages separate concerns without requiring networking and cross-service transactions.
5. **Why DynamoDB?** Explicit partition access and conditional transactions meet the required learning objective. Ad hoc analytics are harder than SQL; the implementation documents bounded queries and does not promise unrestricted indexed search.
6. **How is data partitioned?** Tenant records share `ORG#tenant` as partition key, with distinct sort-key prefixes. Device list/detail, serial reservation, policies, historical versions, evidence and audit each have a specific access pattern.
7. **Can a forged cursor expose another tenant?** No: the cursor contains only a sort key and must match the requested prefix. The repository reconstructs the partition from the service-authorized tenant. Cursor opacity is not an authorization boundary.
8. **How does authentication work?** The browser uses OIDC authorization code with PKCE through Keycloak. The API validates signed access-token issuer, audience, expiry and signature; the simulator uses client credentials.
9. **How is authorization different?** A valid token is insufficient. Every tenant service checks its signed organizations map and required role before reading records. Platform roles grant no implicit tenant membership.
10. **How are memberships revoked?** The initial design trusts provider-issued short-lived claims. Existing tokens remain usable until expiry; stronger immediate revocation or server-side membership lookup is future work.
11. **How do you prevent duplicate devices?** Registration atomically creates the device, a canonical serial reservation and an audit event. An existing serial fails the transaction, preventing a second device or partial audit record.
12. **How do you prevent lost updates?** Each record has a revision. A mutation supplies or reads the expected revision and commits with a conditional expression. A concurrent change yields 409 rather than overwriting state.
13. **How are duplicate reports handled?** The latest accepted report stores sequence, ID and canonical payload digest. An exact replay is a no-op; altered payloads or stale sequence/time are rejected. It is bounded last-report deduplication rather than an indefinite ledger.
14. **How are compliance rules extensible?** The Engine maps rule types to simple strategies operating on a device snapshot and evaluation time. It returns typed rule results; persistence and authentication stay outside the engine.
15. **What does missing telemetry mean?** Missing required values are UNKNOWN. Any failure dominates unknown, unknown dominates pass, and an empty applicable set is NOT_APPLICABLE. Severity is retained as evidence but does not waive lower-severity failures.
16. **How do OS versions compare?** Numeric segments are compared as integers, padding missing trailing segments with zero. Thus 15.10 exceeds 15.9, and 15 equals 15.0. Validation bounds the accepted numeric format.
17. **What happens when a policy changes?** The current policy revision changes conditionally while an immutable historical version and audit record are written. Old evaluations retain the version they used. Fleet-wide automatic re-evaluation is not implemented; a report or explicit device evaluation applies current policies.
18. **How trustworthy is the dashboard?** It reads persisted tenant devices with bounded paginated Queries, excludes retired devices from posture/freshness distributions, and excludes unknown/not-applicable devices from the pass/fail percentage. It is a live multi-page view, not a transactionally frozen analytics snapshot, and rejects fleets over 1,000 devices.
19. **What tests actually ran?** Consult VALIDATION.md. Java unit and DynamoDB Local integration tests, real signed-token validation, frontend tests, production compilation, simulator tests and a manual real-browser workflow are distinct evidence. A GitHub startup failure or unavailable Docker is not described as a passing CI run.
20. **How would you host and scale it?** The target is Fargate, DynamoDB, CloudWatch and S3/CloudFront with production OIDC. Only the initial Terraform foundation is prepared. Before scaling, measure load, introduce materialized aggregates/indexes and consider SQS ingestion if synchronous latency becomes a problem. No throughput, cost saving or production adoption is fabricated.
21. **What should happen during a temporary database outage?** Readiness becomes unavailable so traffic can be withheld, while liveness stays healthy if the process is functioning. FleetOps explicitly separates these probes; tests simulate failure/recovery at the DynamoDB client. Known SDK failures map to a safe503 response. This is not proof of a deployed load-balancer configuration.
22. **Can a successful device write leave an audit failure behind?** Device/evidence/audit writes use one DynamoDB transaction. A regression test forces a revision-condition failure and verifies no extra audit record was committed. Evaluation also happens before the write. This guarantee does not cover arbitrary external side effects, which the current flow avoids.
23. **What does a passing build prove about CI/CD?** It proves compilation and the checks actually executed in that environment. This project has local passing tests but remote Actions startup failures, incomplete Docker verification and no deployment workflow. Build success must not be represented as successful remote delivery.
24. **Which security weaknesses remain?** Report IDs are remembered only for the latest report, production token-type/scope policy is not specified, rate limiting and persistent denial audits are absent, and the machine role can register devices pending A2. Tenant checks and JWT validation address specific threats, not an overall production-security certification.
25. **How did AI assistance affect engineering quality?** It accelerated implementation but also introduced mistakes caught by compilation, browser inspection and regression tests. The audit records the lifecycle/compliance mismatch and a health-group naming error rather than hiding them. Independent tests, diff inspection and evidence-based claims are necessary regardless of who wrote the code.
