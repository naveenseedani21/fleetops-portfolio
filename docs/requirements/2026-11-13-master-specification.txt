# 1. PRODUCT VISION

## 1.1 What Is FleetOps?

FleetOps is a multi-tenant enterprise device inventory, security policy, and compliance management platform.

It allows organizations to:

- Register and manage devices.
- Monitor device security posture.
- Define organization-specific security policies.
- Evaluate devices against those policies.
- Detect noncompliant devices.
- Review device activity.
- Investigate compliance failures.
- Maintain audit histories.
- Visualize security and operational metrics.

The platform focuses primarily on Apple devices:

- MacBook Air.
- MacBook Pro.
- iMac.
- Mac mini.
- iPhone.
- iPad.

However, the domain model should be extensible to additional device families.

## 1.2 Important Product Boundary

FleetOps is **not an actual Apple MDM server**.

It does not enroll physical Apple devices through Apple's Automated Device Enrollment, issue real MDM commands, or remotely control devices.

The MVP uses synthetic device reports produced by a simulator.

The system should model enterprise device-management workflows realistically without claiming functionality it does not possess.

Do not use Jamf trademarks, proprietary UI designs, private APIs, or protected product assets.

The project should be independently branded.

## 1.3 Target Users

FleetOps has three primary user personas.

### Platform Administrator

Responsible for platform operations and organization provisioning.

Permissions must be narrowly defined.

A platform administrator must not automatically bypass tenant data isolation.

### Organization Administrator

Responsible for an organization's device inventory and security policies.

Can:

- Register devices.
- Modify permitted device metadata.
- Retire devices.
- Create and update policies.
- Review compliance reports.
- Review audit events.
- Manage authorized organization users.

### Organization Viewer

Responsible for monitoring and reporting.

Can:

- View device inventory.
- View compliance information.
- View permitted audit information.
- Export authorized reports.

Cannot modify devices, policies, or users.

Create a complete permission matrix before implementing authorization.

## 4.1 Architecture Pattern

Use a modular monolith with clear boundaries.

Each module should separate:

- Application/service layer.
- Domain logic.
- Persistence infrastructure.
- DTOs and mapping.

Keep domain logic independent of HTTP and DynamoDB implementation details wherever practical.

Use constructor injection.

Avoid field injection.

## 4.2 Architecture Diagram

Create a Mermaid architecture diagram showing:

- Identity provider.
- Spring Boot backend.
- Device simulator.
- DynamoDB.
- Audit persistence.
- CloudWatch.

## 4.3 Data Flow

The main device-report workflow must be:

1. Simulator creates a device report.
2. Simulator authenticates using an appropriate machine identity.
3. Backend validates authentication.
4. Backend validates organization scope.
5. Backend validates payload structure.
6. Backend checks report idempotency.
7. Backend checks report ordering.
8. Backend persists accepted device state.
9. Compliance engine evaluates relevant policies.
10. Backend persists compliance results.
11. Backend records audit events.
12. Dashboard displays updated state.

Explicitly define consistency guarantees.

Do not imply that several independent DynamoDB writes are automatically atomic.

Use DynamoDB transactions where atomicity is required and supported.

For multi-step operations that cannot be atomic, implement an explicit recovery or reconciliation strategy.

# 6. AUTHENTICATION AND AUTHORIZATION

Security must be implemented early, not added at the end.

## 6.1 Authentication Strategy

Use a standards-based OpenID Connect identity provider.

For local development, use a containerized identity provider such as Keycloak if practical.

For AWS deployment, choose a suitable managed or external identity provider and document its cost and configuration.

The backend must validate:

- JWT signature.
- Issuer.
- Audience.
- Expiration.
- Not-before claims where applicable.
- Token type and relevant scopes.

Use authorization code flow with PKCE for the Angular application.

Do not store long-lived access tokens in localStorage as the default architecture.

Document token storage, refresh, logout, and XSS tradeoffs.

## 6.2 Machine Authentication

The Python simulator must not use an administrator's password.

Use a dedicated machine identity with limited permissions.

Prefer OAuth 2.0 client credentials where supported.

Machine tokens must only authorize device-report operations for explicitly permitted organizations.

## 6.3 Tenant Isolation

Never trust a frontend-supplied organization ID by itself.

The backend must verify that the authenticated principal has access to the requested organization.

Every tenant-scoped repository operation must include the organization boundary.

Test:

- Tenant A cannot read Tenant B devices.
- Tenant A cannot modify Tenant B policies.
- Tenant A cannot view Tenant B audit records.
- Viewers cannot modify resources.
- Simulator identities cannot invoke administrator endpoints.

## 6.4 Permission Matrix

Create:

`docs/security/PERMISSIONS.md`

Define authorization for every endpoint and role.

Use deny-by-default behavior.

# 8. SECURITY POLICY ENGINE

This is one of the project's most important components.

Build it as a standalone, testable domain service.

## 8.1 Policy Types

Implement:

1. Minimum operating system version.
2. Encryption required.
3. Screen lock required.
4. Firewall required where supported.
5. Maximum check-in age.
6. Allowed device types.

## 8.2 Policy Evaluation

Each rule returns:

- PASS
- FAIL
- UNKNOWN
- NOT_APPLICABLE

Each result includes:

- Rule identifier.
- Evaluation status.
- Human-readable explanation.
- Expected value.
- Observed value where safe.
- Severity.

## 8.3 Aggregation Rules

Define explicit status precedence.

Suggested behavior:

- Any applicable failed rule makes the policy noncompliant.
- All applicable rules passing makes the policy compliant.
- Missing required evidence produces unknown when no applicable rule has failed.
- A policy with no applicable rules produces not applicable.

Device-level aggregation must follow documented rules.

Do not treat missing telemetry as passing.

## 8.4 OS Version Comparison

Do not compare OS versions as ordinary strings.

Implement a version parser and comparator suitable for the supported Apple OS version formats.

Handle:

- Major versions.
- Minor versions.
- Patch versions.
- Missing components.
- Invalid versions.
- Unsupported formats.

Document limitations for prerelease and build identifiers.

Test cases should include:

- 14.10 versus 14.9.
- 15.0 versus 14.9.
- 15.1 versus 15.1.0.
- Missing OS version.
- Invalid version string.

## 8.5 Policy Versioning

Editing a policy creates a new immutable policy version.

Historical evaluations must reference the exact version used.

Do not rewrite historical evaluations when a policy changes.

Implement re-evaluation of devices after relevant policy updates.

## 8.6 Evaluation Reliability

Tests must cover:

- Missing device fields.
- Inapplicable policies.
- Conflicting policies.
- Invalid policy definitions.
- Disabled policies.
- Multiple applicable policies.
- Historical policy versions.
- Repeated evaluations.
- Concurrent policy changes.

# 9. DEVICE REPORT INGESTION

## 9.1 Report Contract

Required fields:

- reportId
- organizationId
- deviceId
- sequenceNumber
- reportedAt
- operatingSystemVersion
- encryptionEnabled
- screenLockEnabled
- firewallEnabled where applicable

## 9.2 Idempotency

Repeated delivery of the same report must not create duplicate state changes or duplicate compliance evaluations.

Use a unique report ID and conditional persistence.

If the same report ID is reused with a different payload, reject it with a documented conflict response.

## 9.3 Ordering

Use per-device sequence numbers or another explicitly defined ordering mechanism.

Reject or safely ignore stale reports.

Do not allow an older report to overwrite newer device state.

## 9.4 Failure Handling

Handle:

- DynamoDB throttling.
- Temporary AWS errors.
- Invalid payloads.
- Unknown devices.
- Duplicate reports.
- Stale reports.
- Unauthorized reports.
- Concurrent submissions.

Use bounded retries with exponential backoff and jitter where appropriate.

Do not retry permanent validation failures.

## 9.5 Consistency

Document what happens if device state is saved but compliance evaluation fails.

Provide a reconciliation mechanism or retryable processing state.

Do not silently leave permanently inconsistent data.
